## 源码中确定存在的等待

1. `src/app/native/speech/SpeechSession.swift:124` 开启 `.volatileResults`，没有开启 `.fastResults`。临时结果可以输出，但当前配置并不保证低延迟出字。可对 fastResults 做相同音频 A/B，收益和准确率代价尚未实测。
2. `src/app/src/live_captions.rs:347` 收到临时结果也会更新原文，原文并非统一等到 final 才显示。
3. `src/app/src/caption_scheduler.rs:151` 为原文和译文提供阅读调度。12 个英文词一页通常停留 3 秒；后续页要等当前页阅读时间。中文按字估算，20 个及以上阅读单位即可达到 5 秒上限。当前页修订可立即更新，但下一页会等待；首个结果在无当前页时立即进入显示。
4. 同一调度器以显示队列等待 4 秒作为追赶条件，但只有不超过 6 个阅读单位的短页缩短停留。长页仍按正常阅读速度；达到 8 秒才跳到最新页。这里看不到 ASR 已经落后多少秒，因此音频延迟和显示等待会叠加。不能将每页停留直接当成每条结果额外等待的实测值。
5. `src/ui/src/features/speech/captionTranslation.ts:27` 只接受 `isFinal === true` 的片段用于翻译。这保证译文至少要等到该片段定稿；片段不一定等于完整句子，但可能表现为说完才开始翻译。
6. `src/app/src/interpretation_ai.rs:197` 使用 `stream: false`，整段响应完成才显示译文。翻译调度最多一个活动请求加一个最新待处理片段，仍可能等上一请求结束。请求还会新建 HTTP Client，不能跨请求复用该客户端的连接池，具体成本未测。

原文路径：音频输入 → ASR 临时/最终结果 → 合并 → 阅读调度 → 原生面板。

译文路径：音频输入 → ASR 最终结果 → 翻译请求排队 → 完整网络响应 → 独立阅读调度 → 原生面板。译文不必等原文显示完成；两条显示队列独立。

## 为什么还不能精确归因到每个步骤

本次取得的埋点并非完整端到端链路：ASR 是 5 秒聚合快照；主队列等待仅记录首次结果，本次提取窗口没有该条记录。没有逐片段 final 等待、翻译排队/请求/首 token/完成、原生面板更新时间。

另外，`caption_scheduler.rs:198` 的显示等待日志使用 `eprintln!`。现场 `lsof -a -p 53001 -d 1,2` 显示 stdout 和 stderr 均连接 `/dev/null`，因此当前启动方式下显示等待日志没有保存。不能把“没找到显示积压日志”理解成“没有显示积压”。

## 建议的优化顺序

1. 先补齐可持久保存的分阶段日志，使用会话/片段/修订标识，分清原文与译文；记录首次临时结果、final、入队、请求、完成及面板更新。保留周期汇总，不保存字幕全文或密钥。面板更新回调仍不等于屏幕实际绘制。
2. 原文显示优先追随当前语音，重新评估 12 词分页和 1–5 秒强制停留，长页也应有追赶策略。阅读历史可另保留，避免为了读完旧页挡住新结果。
3. 对 `.fastResults` 使用相同音频验证首字、修订率和准确率，不能仅凭开关名承诺几秒收益。
4. 中文翻译使用带去重/修订失效机制的稳定前缀或短分句触发，降低只等 final 的限制；支持的服务使用流式译文，复用 HTTP Client。翻译首字和完整句延迟分别验收。

当前证据支持“识别结果分批覆盖 + 阅读调度可能追加等待 + 译文等待 final 和完整响应”的解释；尚不支持给这三者精确分配端到端耗时占比。
