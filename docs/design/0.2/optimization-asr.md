# QuickLang ASR 与实时字幕优化设计

> 更新日期：2026-09-20  
> 范围：汇总本轮本地识别、线程调度、字幕展示、翻译流水线及后续优化建议。  
> 状态：主要代码已实现并通过编译及相关自动化测试；真实设备上的权限、离线识别、延迟、长时间运行和图形交互仍需验收。

## 2026-09-20 后续低延迟更新

本文件下文保留上一轮实现基线。最新实现与实测以 [实时字幕延迟优化与验证](2026-09-20-caption-latency-optimization.md) 为准：已补齐持久化关联日志、改为最新文字直接显示、默认启用经过同音频 ABBA 测试的 `fastResults`，并实现稳定短分句触发、SSE 增量译文和原生网络取消。下文第 6 节的阅读等待、第 8 节的仅 final/整段响应，以及第 10 节中相应“尚未实现”内容已被这一后续版本取代。原有窗口、权限、线程和历史录音边界继续有效。

## 1. 目标与边界

目标是实现“本地英文流式识别 + 即时原文 + 可选异步翻译”，兼顾阅读体验和实时性，避免字幕越来越落后。

- 保留 Swift 系统语音核心，不为性能假设重写整个后端。
- 同一路声音使用一个持续识别会话，不将短音频分配给多个独立识别器后再拼接。
- 音频采集、识别、翻译和显示是不同阶段，分别管理生命周期与积压。
- 原文不等待翻译；译文不要求与当前原文逐句对齐。
- 公共语音模块与字幕调度器不依赖同传页面，为未来听说训练复用保留边界；这不表示训练功能已经迁移。
- 不承诺零延迟，不延迟其他应用播放来制造字幕同步，不用语言模型补写未识别的原文。
- 当前本地入口固定英文，支持系统声音或麦克风；混合音源明确拒绝，不静默降级。

## 2. 两条链路分别优化

### 2.1 当前本地流式路径

系统声音经 ScreenCaptureKit 采集，麦克风经 CaptureInputSequenceProvider 采集；音频在原生层适配后持续送入 SpeechAnalyzer / SpeechTranscriber。结果经过原文合并与显示调度送往原生字幕面板；稳定识别片段另行进入翻译请求调度，译文进入独立显示轨道。

本地 ASR 不通过 WebView 搬运 WAV，不依赖云端识别配置。模型就绪后识别在设备上执行；首次模型准备可能联网下载。没有单独的提前下载入口，也不能将在线识别成功当作离线验收。

### 2.2 保留的云端同传路径

原有音频分块、服务转写、翻译及历史功能保留。关于固定五秒 WAV、单 worker 串行识别和翻译、音频 IPC 与回读的优化建议应针对这条路径核查，不能直接套用到本地流式路径。

对于五秒音频一个任务的串行实现，长期稳定处理通常要求平均满足：

\[
T_{ASR}+T_{translation}+T_{storage/transfer}<5\text{ 秒}
\]

这只是对应串行模型的吞吐判断。流水线解耦后，应分别测量各阶段吞吐和队列等待，不能继续用耗时总和代表唯一瓶颈。

## 3. Apple API 与模型资源

- `SpeechAnalyzer` 管理输入和分析会话，`SpeechTranscriber` 执行语音转文字；两者是 26 系列已有能力。
- macOS 27 的 `CaptureInputSequenceProvider` 封装麦克风等 AV capture device 的采集、转换和异步输入，不是其他 App 系统声音捕获接口。
- 27 系列还提供 `AssetInputSequenceProvider` 和 `AnalyzerInputConverter`。它们是输入辅助能力，不是替代识别器的新模型；当前不要求每条路径都使用这些组件。
- 使用 `AssetInventory` 检查、保留和准备英文资源；资源不足或下载失败显式报错，不自动改为云 ASR。
- 使用引擎协商的音频格式。独立 SDK 烟测曾在不兼容 Float32 目标格式下触发框架 trap；不能凭经验固定转换器输出格式。
- 当前识别启用临时结果和音频时间范围。`fastResults` 自 macOS 26 已有，缩小上下文可能降低准确率，作为后续对照参数，不将其列为已开启的性能优化。
- 当前构建最低 macOS 版本为 27，不能继续宣称此实现支持 macOS 15 或 26。

官方依据：[Speech 更新](https://developer.apple.com/documentation/updates/speech)、[SpeechAnalyzer](https://developer.apple.com/documentation/speech/speechanalyzer)、[CaptureInputSequenceProvider](https://developer.apple.com/documentation/speech/captureinputsequenceprovider)、[fastResults](https://developer.apple.com/documentation/speech/speechtranscriber/reportingoption/fastresults)。

## 4. 已实现：后台执行与优先级

### 4.1 执行职责

`SpeechSession` 从 MainActor 会话迁移为使用专用串行执行器的 actor，底层 dispatch queue 使用 `.userInitiated` QoS。

以下应用侧工作在后台执行：

- 模型准备与识别会话组织。
- 麦克风输入转发、识别结果消费和 JSON 编码。
- 同步的麦克风采集 `startRunning` / `stopRunning`。
- 会话停止、取消与尾部排空。

系统音频转换队列 `quicklang.speech.system-pcm` 同样使用 `.userInitiated`。相关任务显式设置适当优先级。MainActor 注册表只维护单会话所有权，使用代次标识避免旧会话清理新会话。

C ABI 回调仍按 FIFO 顺序投递主队列，宿主立即复制字符串并快速返回；AppKit 窗口操作留在主线程。终态之后不能再发送识别结果。实现处理 stop 先于 begin 的竞态，并保留取消、排空超时及资源释放机制。

### 4.2 为什么不并发启动多个 ASR

连续语音依赖上下文，按短片段并发识别可能增加断词、重复、乱序等待以及模型资源竞争。Apple 内部推理由框架管理，应用任务数量不等于模型并行度。

优化的是各阶段并行与应用侧调度，而不是多个识别实例争抢同一音源。多路独立音源、离线批量文件可以另行评估。

QoS 只影响可控任务的调度倾向，不等于控制 Apple 内部推理优先级，也不能弥补算力不足或消除模型上下文等待。未采用实时线程优先级，不宣称未经实测的速度提升。

## 5. 已实现：原文合并

原始问题是每次 ASR 结果直接覆盖整个面板。结果对应音频范围，不保证是一整句话，也不保证包含前文。

`CaptionComposer` 维护有界片段状态：

- 相邻音频范围追加，保留当前语句前文。
- 重叠范围用新结果修订，避免简单追加造成重复。
- 保护已确认结果，不被迟到的临时结果回退。
- 稳定句末后出现新片段，或出现约 1.5 秒音频间隔时开始下一页。
- 页面标识用于合并同一字幕的累计修订，不因每次修订重新计时。
- 状态有界，旧页面事件不回写当前页面。

当前不能保证拆分单次 ASR 结果内的多个完整句子；这属于后续分句优化，不应标为已完成。

## 6. 已实现：双轨字幕显示调度

### 6.1 公共策略、独立状态

原文与译文各持有一个 `CaptionScheduler`，共享算法但不共享显示进度。使用单调时钟和独立交付队列，不要求上下两栏属于同一个音频片段。

首个可显示结果及时展示；当前页面的临时修订可以更新内容，但不重置首次显示时刻。后续页面按阅读时间调度，而不是每次回调立即覆盖。

### 6.2 阅读时间和追赶参数

当前初始参数：

- 正常停留时间：阅读单位数除以 4，限制在 1～5 秒。
- 空格分词语言按词估算，CJK 使用字符阅读单位，避免中文整句被计作一个词。
- 显示队列等待达到 4 秒：进入追赶策略，较短字幕减少停留时间；不超过 6 个阅读单位的短句使用约 0.6～1 秒。
- 等待达到 8 秒：跳过队列内旧字幕，直接显示最新可用条目。
- 队列最多 32 项，单条文本有界；溢出记录日志并淘汰旧条目。
- 100 ms 可取消定时推进，没有新结果到达时也能切换；主队列最多排入一个待执行 tick。

这些值是初始工程参数，不是普适阅读速度或识别性能指标。没有后续条目时保留最后一条，不因停留期满自动清空。

### 6.3 延迟定义与限制

这里测量的是“结果进入显示队列之后的等待”，不是从声音发出到识别完成的端到端延迟。

跳过旧字幕可以消除显示积压，但不能让落后的 ASR 直接追上声音。输入队列有界溢出终止与“自动丢弃旧音频并重建识别会话”是不同策略；后者尚未实现，不将显示追赶误报为 ASR 自动追赶。

## 7. 已实现：原生多行与右键菜单

### 7.1 显示布局

- 深色半透明 NSPanel，背景不透明度 76%，位于屏幕底部并避让 Dock。
- 宽度基于可用屏幕宽度的 92%；宽屏下另有限宽以提高可读性，不保证在所有屏幕上恒为 92%。
- 原文 26 pt、译文 22 pt，各自按实际字体度量使用 1～4 行。
- 单语最小高度约 84 pt，双语约 160 pt；内容增加时向上扩展，底部保持固定，并受屏幕可用空间限制。
- 支持单词边界及 CJK、emoji 组合字符安全处理，避免无条件尾部截断。
- 超过单页最大容量仍需页面选择；不能将最大四行理解为无限长文本完整展示。

### 7.2 交互

移除字幕区域中的悬停按钮，改为原生右键菜单：

- 回到 QuickLang 主页面：恢复主窗，识别和菜单保持可用。
- 开启／关闭翻译。
- 目标语言：中文、英文、日语、韩语、法语、德语、西班牙语。
- 已保存模型配置：展示配置及模型信息，无可用配置时提供设置入口。
- 停止字幕：终止会话并恢复主窗口。

准备成功才隐藏主窗口。关闭、停止、错误及应用退出需清理会话；不使用应用级隐藏操作连同字幕一起隐藏。

## 8. 已实现：独立翻译流水线

### 8.1 请求与显示分离

`captionTranslation.ts` 消费稳定 ASR 片段，复用现有文本变换接口：

- 最多一条未结束请求，加一条最新待处理片段，避免无限网络请求积压。
- 不重复提交整场会议；单条输入限制为 2,000 个 Unicode 码点。
- 英文识别及显示不等待翻译。
- 翻译返回后进入独立显示队列，长句停留、短句追赶与原文复用同一策略。

“请求队列只保留最新待处理片段”意味着过载时允许跳过中间片段，不保证全文逐句翻译；不能用于承诺完整会议记录。

### 8.2 译文可以落后，但不能倒退

原文已更新到下一段，不使较早的有效翻译自动失效。保留内部音频范围、修订和顺序信息用于去重及防倒退，但不要求上下两栏同时对应同一句。

以下结果不得覆盖当前状态：

- 比已经展示的译文更早的乱序结果。
- 已被源片段修订淘汰的结果。
- 切换目标语言、模型、关闭翻译或重新启动会话之前的过期结果。

等待下一条翻译时保留上一条译文并显示状态。普通原文更新甚至清空原文，不清空译文；语言或模型变化应清除旧配置下的译文。

### 8.3 配置、安全和取消边界

用户明确开启翻译后才向所选服务发送文本。模型菜单复用保存的 AI 配置；传给字幕面板的是白名单元数据，不包括凭据。

现有网络请求仍经 `interpretation_transform` 使用配置凭据；“面板不接收凭据”不等于整个原生网络层不接收凭据。

前端使用代次和会话检查抑制过期完成；取消底层原生 HTTP 目前仍是尽力而为，请求槽在真正结束前不会提前释放。Rust 还会检查会话及排队更新代次，但当前 text/status 接口不能独自识别配置变化后才首次到达的旧译文，前端代次防护仍是必要条件。

## 9. 公共模块与文件定位

- `src/app/native/speech/SpeechSession.swift`：后台 actor 执行器、单会话生命周期、模型准备及识别结果。
- `src/app/native/speech/SystemAudioInput.swift`：系统 PCM 采集、转换及音频队列。
- `src/app/native/speech/SpeechCore.swift`：事件、校验、有界输入等基础能力。
- `src/app/src/caption_composer.rs`：按音频范围合并原文。
- `src/app/src/caption_scheduler.rs`：纯显示调度算法，原文／译文复用。
- `src/app/src/live_captions.rs`：C ABI、会话校验、双轨状态、定时调度和窗口桥接。
- `src/app/native/caption/`：AppKit 右键菜单、字体度量、自适应面板。
- `src/ui/src/features/speech/liveCaptions.ts`：前端会话控制与事件订阅。
- `src/ui/src/features/speech/captionTranslation.ts`：翻译请求调度、配置代次及防倒退。
- `src/ui/src/features/interpretation/Interpretation.tsx`：本地入口、配置和原有云端功能入口。

Swift 公共识别核心不依赖窗口，但当前面向字幕的桥接会联动窗口；未来训练接入应复用识别能力而不是强制隐藏训练主页面。

## 10. 后续优化优先级（尚未实现）

### 10.1 测量和翻译触发

建立采集、送入识别器、临时结果、最终结果、翻译排队、首 token、完成及显示的分阶段时间记录。优先输出 p50/p95 和队列积压时长，日志不记录音频、字幕全文或凭据。

稳定 ASR 结果不一定是完整句子。后续结合句末标点、停顿及最大等待时间聚合翻译输入，在上下文完整性与延迟之间取舍。不要简单把五秒分块改成一秒并宣称实时问题已解决。

### 10.2 网络复用、真实取消和流式译文

核查云端请求 `reqwest::Client` 的构造位置，复用连接池；补齐底层取消、超时与有界重试。为支持流式响应的服务增加增量译文，同时保留非流式兼容。

当前异步整段译文不等于流式 token 输出，后者尚未实现。流式临时译文也要使用同一片段修订，不重复入队或重置阅读时间。

### 10.3 翻译调度下沉

当前翻译调度在前端共享模块。后续可迁移到 Rust，由其负责网络、重试、配置和存储，减少隐藏 WebView 生命周期对会话的影响。Swift 继续负责音频与本地识别，不要求整个后端统一改写为 Swift。

### 10.4 录音持久化与旧云端链路

单独核查云端音频分块、Base64／数字数组 IPC、数据库回读和重复保存。目标是音频只保存一次，文本及状态单独更新，并保留故障恢复能力。

当前本地字幕不保存录音，也不自动写入原有云端历史；原生流式识别已实现不能作为可靠录音存储已完成的证据。

### 10.5 ASR 自身过载恢复

先测量音频输入的时长积压和模型吞吐，区分 UI 堵塞、格式转换成本、调度竞争与模型上下文等待。若确有持续识别落后，再设计提示、输入丢弃、时间轴连续性和会话重建策略。不得直接并发启动多个识别器或静默丢音频。

## 11. 验证记录与验收要求

本轮已获得的自动化证据：

- 双轨整合版本 TypeScript 检查通过，相关前端 7 个测试文件、50 项测试通过。
- 调度整合阶段桌面库测试 36 项通过、5 项忽略，包括 8 项调度器和 5 项合并器确定性测试。
- 原生面板严格 clang 编译通过；无 WindowServer 的沙箱环境下 GUI 测试明确跳过，不计为通过。
- 线程迁移后的 Swift 6 严格并发和 warnings-as-errors 检查通过，含后台执行、主队列回调、准备取消、stop-before-begin、20 次快速控制循环及 ABI 检查。
- 线程迁移后整应用开发构建和差异格式检查通过。不同阶段的测试结果不能代替统一真机性能报告。

仍需验证：

1. 最终应用包的系统声音／麦克风权限、首次模型准备和权限拒绝恢复。
2. 模型就绪后断网转写，确认本地原文不依赖翻译服务。
3. 真实音频的识别质量、首次出字、最终确认、显示等待和翻译延迟。
4. 长短句、多行、CJK、超长词、快速修订、软硬积压阈值及跨屏／全屏显示。
5. 切换语言或模型、返回主窗、连续启停、停止尾部、迟到回调及翻译失败。
6. 至少 30 分钟的队列、内存、发热、耗电和音频路由切换。
7. 线程迁移前后同设备、同音频、同模型资源条件的对照；无实测前不宣称 QoS 带来具体速度收益。

维护时明确区分“设计目标”“代码实现”“自动化验证”“真机验收”，并记录设备、系统、模型资源、音源和测试日期。
